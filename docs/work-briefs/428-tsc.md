## Comparison

- Peer `src/core/cpu_patches.cpp` adds ~335 lines: window scan, branch/data veto, near trampoline, 32.32 fixed-point guest/host TSC scaling and register, flags, red-zone preservation. It may skip unsafe windows. Peer also changes `core/libraries/kernel/{time.cpp,process.cpp,kernel.cpp}` and headers, including guest TSC/frequency, process counter, sysctls and mode switching.
- `crates/runtime/src/cpu_patch.rs` uses iced-x86 and its own window/thunk machinery for BMI1/LZCNT/MOVBE, not shadPS4's Zydis/Xbyak patcher; `wanted` has no RDTSC. `src/probe.c:1907-1921` runs red-zone patching then CPU patching. `BB_CPU_PATCH=0` disables the existing patcher; `all` forces its supported instruction rewrites. Both Linux `build.sh:116` and Windows `gpu/CMakeLists.txt:292` use Rust CPU patching; `src/cpu_patch.c` is retained source, not a separate production path to modify.
- `crates/runtime/src/kernel.rs:709-728,879-885` measures host TSC frequency and returns raw host RDTSC to guest calls; process counter is monotonic nanoseconds with a 1 GHz frequency (`:867-876`). `gpu/shim/bbgpu.cpp:174-178` independently reads fenced raw TSC and shares measured host frequency, while process time stays in nanoseconds. Video output records these TSC values (`videoout/driver.cpp:537,631,825`). Scaling one path alone would give the guest and GPU inconsistent timestamps. Current raw counter/frequency match by design; that does not prove game code never assumes a console rate.
- `kernel.rs:1184-1235` implements only a small sysctl subset; mode changes and peer sysctl behavior cannot be assumed present. The peer's ~322-line kernel.cpp change cannot be dropped in as-is. Existing guest ABI symbols and `BB_CPU_PATCH` behavior must be preserved explicitly.

## Recommended decomposition and acceptance

1. Specify one guest clock contract for inline RDTSC, guest API, GPU flip/vblank timestamps and reported frequency, separate from the existing nanosecond process counter; define fixed-point overflow, rounding, frequency measurement failure, monotonicity and any mode transition. Decide opt-in/override behavior while retaining `BB_CPU_PATCH=0` and `all`; do not change public C or guest ABIs accidentally.
2. Build synthetic Rust rewrite coverage first: short instructions, jump targets, RIP-relative addressing, overlapping windows, invalid/data-adjacent bytes, skipped windows, far trampoline failure, concurrent or repeated patching, and interaction/order with red-zone and existing CPU patch passes. Execute generated thunks with controlled registers, flags and red-zone sentinels, compare scaled EDX:EAX against a reference, and cover zero/overflow boundaries. Failure must leave guest code valid and report unpatched sites.
3. Wire the shared clock to guest and GPU paths together, with deterministic fake-counter tests proving rate, frequency and timestamp consistency; retain process-counter units unless deliberately changed and tested. Add any needed sysctl/mode behavior only with specified guest ABI tests. Run Linux and Windows builds and synthetic harnesses, then separately assess device behavior without including game data.

This is a substantial cross-component design, not a bounded direct import. No production change or assertion that the fix is unnecessary was made. No game files used; no build or gameplay test run in this audit. Host machine class: SteamOS Strix Halo laptop/tablet.
